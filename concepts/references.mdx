---
title: "References"
description: "Wiring services together with ${{service.VAR}}."
---

Env values in `uniac.yaml` may embed references, resolved by the platform at
deploy time and injected at container start:

```yaml
env:
  OWN_URL:      "http://${{self.host}}:8080"        # own builtin
  GREETING_ALT: "${{self.GREETING}}"                # own variable
  DB_HOST:      "${{database.host}}"                # another instance's builtin
  DATABASE_URL: "${{database.DATABASE_URL}}"        # another instance's variable
```

One grammar everywhere: `${{scope.VAR}}`, where `scope` is `self` or an
instance name, and `VAR` is a declared variable or the builtin `host`.

## Resolution rules

- **Scope names an instance, not a definition.** `${{database.X}}` names the
  deployed instance `database`, whatever service resource it draws `from`.
  Getting this backwards is the most common wiring bug.
- **`self`** is the reflexive scope: the declaring service's own builtins and
  variables.
- **`host`** is the only builtin — the platform-allocated internal hostname,
  the one fact the platform contributes to the environment. The env key `host`
  is reserved for it; declaring your own is an error.
- **Names resolve at plan time; values resolve at deploy time.** `uniac plan`
  verifies that every reference to `self` or to an instance in the deployed
  set names a variable that exists.
- **No escape syntax exists.** Any `${{` that does not parse as a reference is
  an error, so a literal `${{` cannot appear in an env value.

## Cross-deployment references

A reference to a name *outside* the deployed set passes through unresolved and
is resolved remotely against the project's other services. This is how
services in separate deployments wire together — and it is why a typo in a
cross-deployment reference cannot be caught locally.

**A dangling reference never fails a deploy.** The affected variable is left
unset and the run reports a warning in the state block. Check the `warning`
lines on every deploy; an unset `DATABASE_URL` is otherwise a runtime mystery.

## Consumer propagation

After a successful deploy the platform re-resolves the project's other
services and recreates any whose injected values changed. Deploy order is a
convenience, not a requirement: a consumer deployed before its provider comes
up with the variable unset, then is recreated with the real value once the
provider lands. Deploying the provider first just skips the broken window.

## Export URLs, not fragments

No service declares the port it binds, so a consumer cannot derive one. Have
the provider export the whole connection string and reference that:

```yaml
db:
  type: stateful
  image: postgres:16
  env:
    POSTGRES_PASSWORD: "change-me"
    DATABASE_URL: "postgres://postgres:${{self.POSTGRES_PASSWORD}}@${{self.host}}:5432/app"

api:
  type: service
  image: ghcr.io/acme/api:1.4.0
  env:
    DATABASE_URL: "${{database.DATABASE_URL}}"
```
