A service is a named application component within a project. Each replica
runs a container from an OCI (Open Container Initiative) image, which supplies
the application and its runtime dependencies. The image can be supplied
directly or built from a Dockerfile. Uniac adds no SDK or runtime dependency
to the application.

## Definitions and deployments

A **service definition** supplies reusable image and runtime configuration.
A **deployment declaration** instantiates it as a service in the target
project, named by the declaration. Several declarations can instantiate one
definition, each as its own service. Deploying the project includes the
service of every deployment declaration.

A service's **replicas** are its running containers. Its identity persists
across replica replacements and deployment versions.

Stateless services can run multiple container replicas behind the same
service identity. A singleton service runs at most one replica at a time:
during replacement, the previous replica stops before its successor starts.
Data that must outlive a replica is written to a
[volume](/resources/volume) bound to the service.

## Required and optional configuration

| Information | Required | Meaning |
|---|---|---|
| Execution type | Yes | Stateless or singleton. |
| Container source | Exactly one | An OCI image reference or a Dockerfile build source. The image platform is `linux/amd64`: a referenced image provides it, and a build targets it. |
| Environment variables | No | [Environment values and references](#environment-and-references). |
| Start command | No | Replaces the image's startup command (`ENTRYPOINT` and `CMD`) at runtime; the image is unchanged. |
| vCPUs | No | 1 or 2 whole vCPUs per container. Omitted, the service keeps its current vCPUs, and a new service gets 1. [Size](#size). |
| Memory | No | 512 to 4096 MiB per container. Omitted, the service keeps its current memory, and a new service gets 512 MiB. [Size](#size). |
| Volume | No | [Durable storage](/resources/volume) for a singleton service. |
| Replica count | No | 0 to 4 for a stateless service, 0 or 1 for a singleton; a new service runs one. [Deployment versions](#runtime-and-deployment-versions) apply it. |
| Public exposure | No | [Public endpoints](#public-endpoints) declared with the service's deployment. |

A start command is split into arguments with shell-style quoting, and its
first argument is executed directly.

### Build source

A build source identifies the source tree, build context, Dockerfile, and
target stage. Each setting has a default:

| Field | Required | Meaning | Default |
|---|---|---|---|
| `root` | No | Path relative to the defining manifest's directory | `.` |
| `context` | No | Path relative to the build root | The root itself |
| `dockerfile` | No | Path relative to the build root | `Dockerfile` |
| `target` | No | Dockerfile stage name | Last stage |

Paths are relative and checked lexically: `root` must stay within the
defining package directory, and `context` and `dockerfile` within the root.
In a workspace, each included manifest keeps its own source directory, and its
build context stays within that package.

## Networking and endpoints

Within its project, a service is addressable by its name, such as `cache`, on
any port its application listens on; internal communication needs no port
declarations. A service is private to its project until it declares a public
endpoint.

The application chooses its listen port, and each public endpoint names that
port. An application that reads `PORT` gets it from a declared
[environment variable](#environment-and-references).

### Public endpoints

A public endpoint forwards incoming traffic to the application's listen port.
Endpoints are declared with the service's deployment declaration,
independently of its reusable definition.

| Type | Allocated endpoint |
|---|---|
| `http` | An address at `https://<hostname>` that Uniac issues on the shared HTTP edge, routing to the application's specified port. A request times out after 60 seconds. |
| `tcp` | A public hostname and port that Uniac issues, forwarding raw TCP to the application's specified port. The public port is allocated independently of the listen port and stays allocated while the endpoint exists. |

Public exposure is optional. Each requested endpoint specifies:

| Field | Required | Meaning |
|---|---|---|
| `port` | Yes | The application's listen port, as a number truncated toward zero. |
| `type` | Yes | `http` or `tcp`. |

Each service can have one `http` and one `tcp` endpoint, on ports 1–65535.

## Environment and references

Environment variables provide runtime configuration to a service's containers.
Their values can refer to the service's own configuration or to another
service declared in the same package. The platform resolves declared values
when the deployment is created and injects them at container start. Other environment
defaults are the image's own.

Environment configuration is optional. Each declared variable requires a
name and a plaintext string value, optionally containing references. Names
match `^[A-Za-z_][A-Za-z0-9_]*$`; `host` is reserved for the builtin reference.
A service accepts at most 64 declared variables, with names up to 128
characters and values up to 4096 characters.

Declared values are stored with the deployment, and the dashboard shows the
serving deployment's values. Changing a value deploys a new version.

### References

A reference's scope names a service, independently of its definition
name. `${{self.VAR}}` names a variable on the declaring service.
The one builtin, `host`, is the referenced service's internal hostname, which
is its name: `${{cache.host}}` is `cache`.

References have this grammar:

```text
\$\{\{\s*([a-z0-9][a-z0-9_-]*|self)\.([A-Za-z_][A-Za-z0-9_]*)\s*\}\}
```

Chains resolve transitively. Across a chain, `self` remains bound to the
service that declared each value. Every `${{` opener must form a valid
reference.

### Resolution

References to `self` must name a builtin or a declared variable. Composition
checks references to the other services declared in the package against their
declared variables and builtins. Unknown names, cross-package
references, and ungrounded value-reference cycles fail locally.

Remote references use services with a serving deployment. For those services,
`host` supplies the internal hostname without requiring a running replica;
a custom-variable reference requires that variable in the service's resolved
environment.

A reference resolves when the declaring service's deployment is created,
against the services serving at that moment, and the resolved values stay with
that deployment. A service picks up a new or changed value from another
service on its own next deployment. A variable whose referenced service starts
serving later is omitted with a warning and filled in by that next deployment.

## Size

A service's size sets the CPU and memory of each of its containers. The
vCPU count is a ceiling on the node's shared CPU, and it sets the
container's process limit at 4096 per vCPU. Memory is a hard limit for the
container's processes together: past it, a process is OOM-killed. Each
replica's memory is reserved on the node that runs it, so a replica is
placed only on a node with that much memory unreserved.

The size belongs to a deployment version: a deployment whose declaration
omits a value keeps the serving version's, and a new service gets 1 vCPU
and 512 MiB. A version deployed before sizing runs with 1 vCPU and 256 MiB;
a deployment that omits memory moves it to 512 MiB.

A replica that no node has room for waits with its instance `starting`, and
its deployment stays in progress until a node has room. Deleting the service
always ends the wait. A replica count set in the dashboard replaces a waiting
change to the serving version's count, so a lower count that fits ends that
wait. A new singleton deployment replaces the waiting one; a new stateless
deployment replaces it only once the new version is running, so it needs room
beside the serving version and any replicas the waiting deployment has
already placed. A stateless deployment needs room for its new version beside
the previous one. A singleton's previous replica stops first, so the service
can stay stopped until room appears, even at the same size, when replicas
already waiting take the freed room first.

## YAML composition example

In [YAML composition](/composition/yaml), `type: service` selects
stateless execution and `type: singleton` selects singleton execution. Exactly
one of `image` or `build` supplies the container source; `image: ""` counts
as absent. Optional configuration uses `env`, the `start_command` string,
the `vcpu` and `memory_mib` integers, and the `volumes` list. `env` maps
variable names to string values. A `vcpu` or `memory_mib` that is not an
integer fails locally; one outside its
[range](#required-and-optional-configuration) is rejected at deployment.

`build` accepts a string naming the build root or an object containing the
build fields above. An empty string selects the default root; `build: null`
is invalid. Each build root is relative to the directory containing its
definition's `uniac.yaml`.

A deployment declaration's optional `replicas` is an integer. Omitted or
`null`, the service keeps its current count on deployment.

A deployment declaration's `public_ports` is an optional list of mappings,
each with `port` and `type`. Its presence has three meanings on deployment:

| Value | Result |
|---|---|
| Omitted or `null` | Keeps the service's existing public exposure. |
| `[]` | Removes all public exposure. |
| Nonempty list | Replaces public exposure with exactly this list. |

The `web-code` and `cache-code` resources are definitions, and the `web` and
`cache` deployment declarations instantiate them as the services `web` and
`cache`. The `from` field connects each declaration to its definition in this
package.

The stateless `web` service runs two replicas and receives the URL declared by
`cache`, which uses `cache`'s own internal hostname. The `web` service's port
8080 is exposed through HTTPS and a separately allocated raw TCP endpoint. The
singleton `cache` service starts Redis with 1024 MiB of memory and
append-only persistence on a 1 GiB volume mounted at `/data`.

```yaml
resources:
  web-code:
    type: service
    image: mendhak/http-https-echo:31
    env:
      CACHE_URL: "${{cache.URL}}"
  cache-code:
    type: singleton
    image: redis:7-alpine
    env:
      URL: "redis://${{self.host}}:6379"
    start_command: redis-server --appendonly yes
    memory_mib: 1024
    volumes:
      - name: data
        size_gb: 1
        mount_path: /data
  web:
    type: deployment
    from: web-code
    replicas: 2
    public_ports:
      - port: 8080
        type: http
      - port: 8080
        type: tcp
  cache:
    type: deployment
    from: cache-code
    public_ports: []
```

The generated description uses `container.source.ref` for `image` and
`container.source.build` for `build`. `type: singleton` adds `kind: singleton`,
while `type: service` omits `kind`. Build paths are normalized and omitted at
their defaults; an all-defaults build is `{}`.

## Runtime and deployment versions

In live state, a deployment is a version of one service, with its own
lifecycle and running containers. Redeploying a declaration updates its
service, and a service keeps its execution type across versions; a deployment
that changes the type is rejected.

Each `uniac deploy` creates a new version of every declared service. The new
version runs the declaration's `replicas` count. Without one, it keeps the
requested count of the serving version, or of the newest `active` version
when none is serving, including zero; a service with neither starts with one
replica. The new version replaces the running replicas; a singleton's previous
replica [stops](#stopping-instances) first.

A deployment succeeds once the platform has started the new version's
containers and stopped and removed the previous versions' containers. It does
not judge how the application runs: a container that exits after it starts
does not fail the deployment, and its [instance](#instances) status shows the
exit. A deployment whose container cannot be started fails. A deployment to
zero replicas completes once the previous containers are removed.

### Instances

Each replica runs as an instance. An instance is `healthy` while its
container's process runs, and it receives new connections only while it is
healthy; connections that arrive before the application listens on its port
are refused. The platform restarts a container whose process exits, and the
instance is `unhealthy` until the process runs again. After five consecutive
restarts that each ran for less than a minute, the container stays stopped
and the instance is `failed`.

| Status | Meaning |
|---|---|
| `starting` | The replica is waiting for placement, or its container is starting. |
| `healthy` | The container has started and its process runs. |
| `unhealthy` | The container has started and its process is not running, such as between restarts. |
| `failed` | The container could not start, or stays stopped after repeated exits. |
| `terminating` | The replica is being stopped. |
| `unknown` | The platform cannot observe the instance at the moment. |

An instance also reports when its container started.

Each instance has a key, a UUID the platform assigns, which it keeps for its
life. The platform can move an instance to another node, and the instance
keeps its key. A new deployment version, a size change, a scale-up and the
replacement of a `failed` instance start instances with new keys.

### Stopping instances

When the platform stops an instance, it removes the instance from routing,
then sends the container's main process the image's stop signal: the
Dockerfile `STOPSIGNAL`, or `SIGTERM` when the image declares none. If the
process has not exited 30 seconds later, the platform kills every process in
the container with `SIGKILL`. Deployments that replace a version, pause,
scale-down, moves to another node, deletion and account holds all stop
instances this way.

While an instance stops, its status is `terminating`. It keeps its volume,
its outbound network, name resolution of its project's services and its
logs, and its usage is metered until its process has stopped. Execs and
terminals running in it end when the stop begins. A deployment, a pause or a
scale-down completes once the instances it stops are gone.

A main process running as PID 1 receives only the signals it handles, so one
that installs no handler for the stop signal is killed after the 30 seconds.
A singleton's successor starts after its predecessor has stopped, on a
deployment and on a move, so the predecessor's shutdown is part of the
replacement's downtime. An instance whose node fails or is preempted can be
stopped without the signal.

### Logs

The platform keeps what each instance writes to stdout and stderr, line by
line, with the stream and the time the platform received the line. A run is
one start of the instance's container: its first start, a restart after its
process exits, and a restart after its node reboots. An instance keeps its
current run, which is the latest, and the run before it. Both are kept across
restarts and while the instance is `failed`. Each run keeps its last 8 MiB of
output. An instance whose container never started has no run.

Logs belong to the instance's placement on its node and are removed with it:
when a deployment replaces the instance's version, when a scale-down, a pause
at zero replicas or the service's deletion removes the instance, and when the
platform replaces it after it is `failed`. When the platform moves an instance
to another node, the instance's runs start over there.

### Exec

An exec runs one command in a running instance's container and returns the
command's output and outcome. The command runs as the container's own
process: the image's user, the instance's environment and the image's working
directory, with the container's capabilities, no-new-privileges, seccomp and
AppArmor, and without a terminal. Its CPU, memory and processes count against
the instance's [size](#size), so a command that exhausts memory can stop the
instance's own process.

| Value | Specification |
|---|---|
| Command | An argument list of 1 to 256 strings, at most 64 KiB together. The first is the program, found on the container's `PATH`; no shell is added. |
| Standard input | Optional, at most 1 MiB, closed once it is written. Without it, standard input is empty. |
| Timeout | 120 seconds, not adjustable. |
| Output | 16 MiB across stdout and stderr. Output beyond it is counted and not sent. |
| Open execs | 4 per account and 2 per instance. |

At the timeout, and when the caller disconnects, the command's own process
receives SIGTERM and, 5 seconds later, SIGKILL. Processes it started are not
signalled and keep running in the container: the other commands of a shell's
pipeline or script, and processes it leaves in the background. Output they
hold open is read for at most 2 seconds after the command exits.

An exec ends with one of these outcomes, unless its stream is cut first, as
when a platform component on its path restarts; the platform then stops the
command as it does on a disconnect, and no outcome is reported:

| Outcome | Meaning |
|---|---|
| `exited` | The command ended by itself, with its exit status, 128 + n for a command ended by signal n. |
| `timeout` | The platform stopped the command at its timeout. |
| `container_stopped` | The instance's container stopped while the command ran, through a crash, a deployment, a pause or the instance's removal. |
| `start_failed` | The process could not be started: the program was not found on the container's `PATH`, the program is not executable, or the process could not be started otherwise. |

After `timeout` and `container_stopped`, the outcome carries the status the
command ended with when the platform observed it. An exec runs only while the
instance's container is running; in an instance that is `starting`,
`unhealthy`, `failed` or `terminating`, it is refused with that state. Each
exec runs its command once, so running it again runs the command again. When
the platform cannot run an exec at the moment, it refuses it, and the refusal
can follow a command that started and was stopped.

The platform records every exec for its operators: who ran which command and
how it ended. The command's standard input and output are not recorded.

### Terminal

A terminal runs a program interactively in a running instance's container,
over one connection. The program runs as an exec's command does, with the
instance's environment and `TERM=xterm`, and its CPU, memory and processes
count against the instance's [size](#size). A pseudo-terminal of the
requested size is its standard input, output and error: Ctrl-C is a byte the
terminal turns into SIGINT for the program in the foreground.

| Value | Specification |
|---|---|
| Command | An argument list of 1 to 256 strings, at most 512 bytes together as UTF-8. The first is the program, found on the container's `PATH`; no shell is added. |
| Size | Columns and rows, each 1 to 65535; 80 by 24 when not given. |
| Idle limit | 15 minutes without input. |
| Lifetime | 1 hour. |
| Open terminals | 4 per account and 2 per instance, counted apart from execs. |

A terminal ends when its program exits, after 15 minutes without input,
after 1 hour, or when its connection closes or is lost, including through the
platform's own updates and after 45 seconds without any message from the
client. The program then receives SIGHUP, and SIGKILL 5 seconds later.
Processes it leaves in the background keep running. Nothing resumes a
terminal; run `tmux` or `screen` inside the container to keep a session
across connections.

A terminal ends with one of these outcomes, unless its connection closes
first; the platform then stops its program, and no outcome is reported:

| Outcome | Meaning |
|---|---|
| `exited` | The program ended by itself, with its exit status, 128 + n for a program ended by signal n. |
| `idle` | The platform ended it after 15 minutes without input. |
| `deadline` | The platform ended it at its 1-hour limit. |
| `container_stopped` | The instance's container stopped while it ran, through a crash, a deployment, a pause or the instance's removal. |
| `start_failed` | The process could not be started, for the same reasons as an exec's. |

A terminal runs only while the instance's container is running; in an
instance that is `starting`, `unhealthy`, `failed` or `terminating`, it is
refused with that state. It is also refused at either cap, for a command
over 512 bytes or a size out of range, and when the platform cannot start it
at the moment. That last refusal can follow a program that started and was
stopped.

The platform records every terminal for its operators: who opened which
program, its size, and how it ended. What was typed and the output are not
recorded.

### Observed state

| Fact | Meaning |
|---|---|
| Serving version | The service deployment currently serving, identified by its version number. |
| Lifecycle | The deployment's phase: `preparing`, `active`, `retiring`, or `retired`. |
| Size | The serving version's vCPUs and memory in MiB. |
| Requested replicas | The requested container count. |
| Effective replicas | The container count after platform policy is applied. |
| Observed replicas | The number of instances that are `healthy` or `unhealthy`; unreported while the platform cannot observe one of the replicas. |
| Instances | Each [instance](#instances)'s status and start time, a previous version's included while it stops. |
| Deployment task | A deployment operation in flight, with its own state and current step. |
| Hold | A platform-side reason the service is not converging. |
| Warning | A non-fatal condition reported by the platform. |

### Dashboard and removal

A service's dashboard page shows its state, public endpoints, deployment
activity and resource usage. It sets the replica count (0 to 4 for a stateless
service, 0 or 1 for a singleton), which later deployments keep unless their
declaration sets `replicas`. It also changes public endpoints and offers
**Delete service**, confirmed by typing the service's name.

The project's **Logs** page, beside its graph, shows a service's
[logs](#logs) for one instance or all of them: **Follow** adds output as it
is written, and **Previous run** shows the run before the current one. A
service's **Console** opens a [terminal](#terminal) in an instance, running
`bash` where the image has it and `sh` otherwise. A terminal lasts while the
service's window stays open; choosing another instance ends it and opens one
there. After a terminal ends, **New terminal** opens another.

Deleting a service stops its replicas and removes its deployments, images and
public endpoints. The service reports `terminating` until the removal
completes, and is then gone. Its volume is unbound and keeps its data; the
[volume lifecycle](/resources/volume#lifecycle) governs its retention and
deletion.
