By the end, a coding agent — Claude Code, Codex, or anything that reads
`~/.agents/skills` — can take your application from "deploy this" to a running
service, and you can verify everything it did. You need Node 18+, a running
Docker daemon, and a prebuilt container image; Uniac deploys images, it does
not build them.

## 1. Install the CLI and log in

The two steps that need a human: installing the binary the agent will drive,
and authenticating it.

```bash
npm i -g @uniac/cli
uniac auth login
```

`login` opens a browser and stores the session in `~/.uniac/auth.json`; every
`uniac` command the agent runs uses it. For machines without a browser, see
[Headless environments](#headless-environments) below.

## 2. Give your agent the contracts

```bash
git clone https://github.com/uniac-ai/UniacAppSkill && bash UniacAppSkill/install.sh
```

This installs the Uniac agent skills: the model, the full manifest schema,
the CLI's output and exit-code contracts, and multi-service composition. The
agent works from the shipped contracts instead of guessing from memory.

## 3. Ask for a deployment

Tell the agent what should run, not which commands to run:

```text
Deploy this on Uniac: image ghcr.io/acme/api:1.4.0, listening on 8080, public over HTTP.
```

The agent authors `uniac.yaml` — one file, the whole system description:

```yaml uniac.yaml
runtime: yaml
default: main
resources:
  api:
    type: service
    image: ghcr.io/acme/api:1.4.0
  main:
    type: deployment
    services:
      api:
        from: api
        public_ports: [{ port: 8080, type: http }]
```

and verifies it with `uniac plan` — offline, no credentials, no Docker. A
manifest that fails `plan` fails `deploy` with the same error, so this is
where the agent iterates:

```text
Deployment: main
Artifact:   sha256:d15249bcf885

Building
  pull ghcr.io/acme/api:1.4.0

Deploying
  api  ghcr.io/acme/api:1.4.0  public: 8080 (http)
```

Once the plan is clean, the agent binds the directory to a project
(`uniac link`) and ships (`uniac deploy`), which pushes the image, registers
the deployment, and watches until the platform settles — ending with the
state block:

```text
project  my-app-e5f6g7h8

service  api  v1
  image  ghcr.io/acme/api:1.4.0
  digest  sha256:…
  status  running (1/1)
  endpoint  https://<allocated-host>.svc.uniac.ai → :8080
```

## 4. Verify what the agent did

```bash
uniac status
```

Re-observes the project and prints the same state block; it changes nothing.
The `endpoint` line is your service's public address, `v1` is the serving
deployment, and a `warning` line is a condition worth reading. Everything the
agent did is re-readable — the platform's account, not the agent's.

Prefer to drive the commands yourself? They are all in the
[CLI reference](/cli/overview).

## The contract the agent works against

- **`uniac plan` is the test suite for `uniac.yaml`.** It reproduces every
  [manifest error](/concepts/manifest#what-fails-at-plan-time) offline, and
  `uniac plan --json | jq -r .digest` is a content-addressed change detector —
  a moved digest means the system moved.
- **Exit statuses are typed and closed** — branch on them, read the `error`
  code in the [run output](/cli/output) for detail, and never match on the
  message: it is prose for people. See [Exit codes](/cli/exit-codes).
- **Check `warning` lines on every deploy.** A dangling
  [cross-deployment reference](/concepts/manifest#cross-deployment-references)
  does not fail the run; it leaves the variable unset and warns.
- **Interrupting a deploy does not cancel the platform-side work** — `uniac
  status` re-observes where it landed.

## Headless environments

For CI or an agent host without a browser, skip `uniac auth login` and
`uniac link` and set two variables — everything else works the same:

```bash
export UNIAC_ACCESS_TOKEN="…"                 # from `uniac auth token` on a logged-in machine
export UNIAC_PROJECT_URL="my-app-e5f6g7h8"    # full URL or bare slug
```

Without a link binding and without `UNIAC_PROJECT_URL`, `uniac deploy` drops
into an interactive project picker — which hangs a non-interactive caller, so
always set one of them in CI. Docker must be available on the runner.

| Variable | Effect |
|---|---|
| `UNIAC_ACCESS_TOKEN` | Bypasses interactive login. |
| `UNIAC_PROJECT_URL` | Targets a project, bypassing `.uniac/deploy.json` and the picker. |
| `UNIAC_PROGRESS` | `1` forces progress narration on stderr, `0` silences it. Never affects stdout. |
| `UNIAC_STORE_DIR` | Local artifact store location (default `~/.uniac/store`). |
| `UNIAC_AUTH_HOST` | Host serving the `/cli/auth` login handoff (default `uniac.ai`). |

Narration goes to stderr only when stderr is a terminal, so CI logs stay
clean by default; `UNIAC_PROGRESS=1` shows live progress anyway.
