## Channels and formats

`deploy` prints one final text report to stdout, containing its execution
record followed by the state it could report. `status` prints the state and,
if its read fails, an error block. `service delete`, `volume delete` and
`project delete` print their outcome or the same error block, and ask their
confirmation question on stderr. `logs` prints instance output on stdout, and
its notices and error blocks on stderr. `exec` prints its command's stdout
on stdout and its stderr on stderr, and its own notices and error blocks on
stderr. These reports are text;
`plan --json` is the JSON output. Help and
argument-parsing errors go to stderr and leave stdout empty.

Deployment progress uses stderr. By default, a terminal with usable width
gets a live display that clears when the run ends. `UNIAC_PROGRESS=1` streams
plain progress lines; `UNIAC_PROGRESS=0` turns progress off. These settings
affect stderr only, and progress display applies to `deploy`.

`link` writes its listing, prompt and confirmation to stderr, including when
deployment opens the picker. Other commands write results to stdout and
errors to stderr. A failure to render a status report can also write stderr.

## Plan output

The text preview names the local project and root directory, its optional
description, and the digest of its complete generated description. It then
shows shared image work under `Building` and named services under
`Deploying`. Service rows include sources, declared public exposure, volumes,
a declared replica count and a declared size, grouped by package for a
workspace. `--full`
adds environment values, the start command, and the source definition's
name.

`plan --json` emits `{project, digest, deployable, declarations}`. `project`
contains `root_dir`, `name`, optional `description`, and `packages` with each
package's relative `path`. The root package is `.`. `declarations` associates
each `service` with its `package`, its `deployment` declaration, which has the
service's name, and its `from` definition.
`deployable` is the complete generated service description.
Environment and start-command fields are included whether or not `--full`
is supplied. [Composition in YAML](/composition/yaml#generated-description) defines the generated
description and what its digest identifies.

## Deployment record

The root line names the local project. Its children report `plan`,
`link`, `build`, `push <service>`, `submit <service>`, and `observe <service>`.
They include the digest of the generated description, project slug, image
count, pushed image digest and observed status when available. Displayed
digests are shortened, and image references and digests appear in the record
section.

`✓` marks completion and `✗` marks failure. On failure, the root line carries
an error code and the failed stage includes its retained progress and error
message. An interruption
is classified under the stage in flight, and a nonzero exit can still leave
a report and project or service rows.

### Per-service release outcomes

Each `release` block identifies the service, its package and its deployment
declaration. It records whether the image was pushed, the
submission outcome, returned deployment and task IDs, whether service state
was read, and any failure phase or warnings.

| Submission | Established fact |
|---|---|
| `not attempted` | No registration was initiated for this service. |
| `accepted` | The server acknowledged registration; observed state is reported separately. |
| `rejected` | Registration received an explicit client-error refusal. |
| `acceptance unconfirmed` | Registration was attempted without a conclusive response; the server may have accepted it. |

Failures retain earlier receipts and identify later unattempted work. An
image push, accepted request, or cancellation does not establish the state
of the running service. Releasing again starts a new operation.

## State rows

Service state is explained in
[Service observation](/resources/service#observed-state), public
addresses in [Networking](/resources/service#networking-and-endpoints), and durable
storage state in [Volume states](/resources/volume#states).

| Row | Representation |
|---|---|
| `project` | The linked project's name; deployment falls back to its slug. |
| `platform` | The platform API origin, shown only when it differs from production. |
| `root` | The resolved local project directory, included in deployment reports. |
| `service` | A service name, followed by `v<N>` when a serving version was read. |
| `status` | Reported status, followed by the `(observed/effective)` replica counts when the observed count is reported. |
| `kind` | Reported service kind, omitted when unavailable. |
| `size` | `<N> vCPU, <M> MiB`: the serving version's [size](/resources/service#size), omitted when unavailable. |
| `lifecycle` | Reported serving-deployment phase, omitted when empty or `active`. |
| `deploying` | The in-flight task state and its current step when reported. |
| `replicas` | `<N> requested`, shown when the requested and effective counts differ. |
| `instance` | One row per instance of any version of the service: the short form of its key, as `logs` prefixes its lines ([Log output](#log-output)), then its [status](/resources/service#instances), followed by `, started <time>` in RFC 3339 UTC once its container has started, as in `5b1e0f8c healthy, started 2026-11-03T14:02:07Z`. During a rollout, the previous version's instances show `terminating`. A service without instances has no `instance` row. |
| `endpoint` | `<type> <address> → :<container-port>`; type and container port are omitted when unavailable. |
| Indented `volume` | `<name> at <mount-path>` on a service. |
| `hold` | A platform hold code. |
| `warning` | A platform warning or a CLI observation/recording warning. |

The endpoint address is the complete address a client uses. A TCP address
includes its allocated public port; the number after `→` is the container
port. Columns align within each block, so their character offsets vary.

Whole-project `status` lists services in name order. It and `deploy` add the
project's volume blocks after the services, volumes no service is bound to
included. Each volume block has its name, its `size` in GiB and its `state`.
While a [growth](/resources/volume#lifecycle) is pending, `size` also names
the size it is growing to and, when the platform has recorded it, since when
the growth was requested, in RFC 3339 UTC, as in
`5GiB, growing to 20GiB since 2026-11-01T05:29:54Z`. `state` is
`bound to <service>`, `available (no service is bound; data intact)`, or
`provisioning`, `releasing` or `deleting`. `deploy` and single-service
`status` also show each service's mounts.

### Partial observations and warnings

HTTP 401 or 403 from the platform or project API fails the command. The
following observation fallbacks apply to other errors.

A failed service-detail read during whole-project `status` leaves that
service's name and summary status but omits its additional details. A failed
volume read omits the volume section. Either can occur with exit 0. Missing
rows therefore do not establish that the corresponding remote facts are
absent.

When deployment otherwise succeeds but its read of a service's final state
fails, it reports `state unread` as a warning. A failed local release-record write produces
`release record not written: <error>`; the remote deployment remains in place.
These warnings leave the exit code unchanged. A name-only service row means
registration was accepted but service state was not read; it does not
establish a running service. Rejected and unattempted submissions appear in
release outcomes only.

Platform warnings are passed through, including unresolved
[environment references](/resources/service#environment-and-references).

## Deletion output

A successful `service delete` prints its first line below, and the second for
a volume bound to the service; a successful `volume delete` prints the third,
and a successful `project delete` the last two:

```text
Deleted service <name> from project <project>.
Volume <volume> is unbound and keeps its data; `uniac volume delete <volume>` destroys it.
Deleted volume <name> and its data from project <project>.
Deleted project <name>.
The platform finishes removing its services, endpoints and volumes on its own; the name <name> stays taken until it has.
```

When the platform differs from production, `on <platform-url>` follows the
project name. A failure prints the error block below.

## Log output

`logs` prints each line an instance wrote, on stdout whichever stream it was
written to, without its newline and prefixed with the instance's short form:

```text
[5b1e0f8c] server listening on :8080
```

The short form is the first 8 characters of the instance's key, with more
characters where another instance of the service shares them, as in
`5b1e0f8c-3` and `5b1e0f8c-9`. Each instance's lines are in the order the
platform received them. With `-f`, the instances' lines interleave as they
arrive. A line over 16 KiB, which the platform keeps in parts, prints whole,
and so does a run's last line when its output ended mid-line.

With `--timestamps`, each line begins with the time the platform received it,
RFC 3339 in UTC cut to the second, before the short form. A line the platform
kept in parts has its first part's time, and the pruned-output notice has
none:

```text
2026-11-03T14:02:07Z [5b1e0f8c] server listening on :8080
```

When output was removed before it could be read, as when a followed instance
writes faster than its logs are read, stderr gets a notice and output
continues from the oldest kept line:

```text
[5b1e0f8c] earlier output was pruned before it could be read
```

A service without instances prints `Service <name> has no instances.` on
stderr and exits 0. When an instance's read fails, its error block, below,
goes to stderr and the other instances' output continues; the command exits
with the first failed instance's code, in key order. An interruption ends the
command, which exits 0 unless an instance's read had already failed.

## Exec output

`exec` writes its command's output byte for byte as the platform sends it,
stdout on stdout and stderr on stderr; the order between the two streams is
approximate. What its exit code cannot say gets one line on stderr:

```text
uniac exec: the program was not found on the container's PATH
uniac exec: the program is not executable
uniac exec: the process could not be started
uniac exec: the platform stopped the command at its timeout
uniac exec: the instance's container stopped while the command ran
uniac exec: output truncated: the command wrote <n> bytes to stdout and <m> to stderr, more than the platform sends
```

The first three are a start that failed, which exits 127, 126 and 125. After
a timeout or a stopped container, `exec` exits with the status the command
ended with, such as 143 after SIGTERM; when the platform did not observe that
status, the line ends with `; its exit status was not observed` and `exec`
exits 125. The truncation line follows output past the
[output limit](/resources/service#exec) and leaves the exit code unchanged.

An invalid invocation prints the usage, and an argument that is not valid
UTF-8 or standard input over 1 MiB prints one `uniac exec:` line; nothing is
sent:

```text
uniac exec: argument "<arg>" is not valid UTF-8, which an exec cannot carry
uniac exec: standard input is over 1 MiB, the most an exec sends
```

Any other failure prints the error block below without `retryable`, since
running `exec` again runs the command again. All of them exit 125. An
interruption prints nothing and exits 130.

With `-it`, `exec` writes the terminal's output to stdout as the platform
sends it, and restores the CLI's terminal before it writes anything else. A
start that failed prints the same three lines and exit codes as above. Each
other end besides the program's own exit, and a connection that closed before
the terminal ended, gets one line on stderr:

```text
uniac exec: the terminal ended after 15 minutes without input
uniac exec: the terminal ended at its 1-hour limit
uniac exec: the terminal ended because the instance's container stopped
uniac exec: the connection closed before the terminal ended, and the platform stopped its program
```

After the first three, `exec` exits with the status the program ended with,
or 125 when the platform did not report one; after the last, it exits 125.
These invocations print one `uniac exec:` line and send nothing:

```text
uniac exec: -t requires -i
uniac exec: -t requires a terminal on standard input
uniac exec: the command is over 512 bytes, the most a terminal takes
```

A refused terminal prints the error block, as a refused exec does.

## Errors and exit codes

A `status` error block contains `error <code>`, a human-readable `message`
and `retryable yes` when reported. Deployment puts the code on the root line
and annotates a retryable failure there. `retryable` means the same operation
may succeed without changes; error messages are explanatory prose.

The following exit codes apply to `deploy`, `status`, `logs`,
`service delete`, `volume delete` and `project delete`:

| Exit | Code | Condition |
|---|---|---|
| 0 | — | The command succeeded. |
| 2 | `usage` | Invalid invocation, including `logs -f` with `--previous`, a delete without `--silent` and without a terminal, or a typed name that does not match; nothing is deployed or deleted and no code is printed on stdout. |
| 3 | `auth` | No locally usable credential, or platform/project API HTTP 401. |
| 4 | `not_linked` | Missing binding after credential selection, project absent or mismatched with the binding, `UNIAC_PROJECT_URL` naming no project on the account, binding/platform conflict, or deployment's picker found no projects. |
| 5 | `manifest` | Local project ownership, description validation or deployment-shape failure. |
| 6 | `build` | Docker daemon, image-pull or build failure. |
| 7 | `push` | Image upload failure. |
| 8 | `deploy_failed` | Deployment request/task failure, a refused platform read (including a log read the platform refuses and an `--instance` that matches no instance or several), a delete the platform refuses (including a missing service, volume or project and a volume a service is bound to). |
| 9 | `unreachable` | A platform request was classified as unreachable, or an instance's logs stayed unavailable through five minutes of retries. |
| 10 | `pending` | `deploy`, `service delete` or `volume delete` stopped observing work the platform is still doing, after five minutes. Nothing had failed by then; `uniac status` or the dashboard shows how it ends. For `deploy`, services registered after it are not attempted; deploy again once it finishes. |
| 70 | `internal` | Unclassified failure. |

`exec` prints these codes in its error blocks and exits with the codes in
[Running a command](/cli/overview#running-a-command): `deploy_failed` when
the platform refuses the exec or `exec` cannot choose an instance, and
`unreachable` when the platform cannot run it at the moment, cannot be
reached, or the stream ends before the command's outcome. A terminal uses
the same codes for its refusals and for a platform that cannot be reached.

These commands use the codes above. Some conditions use a code whose name
describes only part of the cause:

- `status` without a binding or target override exits 4 when a credential is
  available; without a usable credential it exits 3.
- Deployment's project picker reports unanswered-input failures as 70;
  no projects produces 4.
- Missing build directories or Dockerfiles produce 5 during planning;
  Dockerfile or daemon failures during image work produce 6.
- Platform/project API HTTP 401 produces 3; HTTP 403 during project checks,
  registration or observation produces 8. Docker registry credential
  rejection remains a push failure (7).
- After a successful first task read, later task-read failures fail the
  command using these classifications.
- Project checks, status reads and deployment push/request operations
  classify transport errors and HTTP 502, 503, 504, 521, 522, 523 and 530 as
  unreachable (9). Other refused API reads, including HTTP 500, produce 8.

Other commands use 0 for success, 1 for command failure and 2 for invalid
invocation. A description failure produces 1 under `plan` and 5 under
`deploy`. Bare or unknown invocations exit 2; help and `version` exit 0.

## Getting help

- [docs.uniac.ai](https://docs.uniac.ai) is the current documentation;
  its [index](https://docs.uniac.ai/llms.txt) lists every page.
- The [Uniac Discord community](https://discord.gg/VR92F2qKjQ) is where
  people ask for help with a deployment.
- support@uniac.ai handles account matters.

Joining the Discord or writing to support is the user's action: a
sign-in or deployment failure that the documentation does not resolve
is reported to the user together with these places.
