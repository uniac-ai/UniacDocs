The `uniac` CLI is a single Go binary, installed via
[`npm i -g @uniac/cli`](/get-started/installation). Check the build with
`uniac version` (also `--version` or `-v`).

## Commands

| Command | Network | Docker | What it does |
|---|---|---|---|
| [`uniac init`](/cli/init) | no | no | Scaffold `uniac.yaml`: one service plus the deployment instantiating it. |
| [`uniac plan`](/cli/plan) | no | no | Resolve a deployment and preview the deployable. The offline verification loop. |
| [`uniac link`](/cli/link) | yes | no | Bind this directory to a remote project. |
| [`uniac deploy`](/cli/deploy) | yes | yes | Resolve, materialize, push, register, then watch until the deployment settles. |
| [`uniac status`](/cli/status) | yes | no | Report what the linked project is running. Changes nothing. |
| [`uniac auth`](/cli/auth) | login only | no | Manage the stored session. |
| `uniac version` | no | no | Print build metadata. |

## Targeting

`plan` and `deploy` target a **deployment**: the named resource, else the
manifest's `default`, else its only deployment. Naming a service is an error —
services are definitions, not deployable targets.

`plan`, `deploy`, and `status` locate the project directory with `--dir`;
`link` uses `-C`.

## Two families of command

`deploy` and `status` report state: each run ends with the
[state block](/cli/output) on stdout and exits with a
[typed status](/cli/exit-codes) from the closed set 0, 2–10, 70.

`init`, `plan`, `link`, and `auth` are human-oriented: they print in their own
shapes and exit `1` on error, `2` on a usage error.
