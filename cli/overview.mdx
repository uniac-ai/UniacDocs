The `uniac` CLI connects a local application composition to a remote project.
Its commands prepare descriptions, deploy services, and read live state.

`npm install -g @uniac/cli` installs the `uniac` command with Node 18+.
`npx -y @uniac/cli …` runs the same command without a global installation.
This reference describes release 0.3.34.

## Invocation

Local directory options default to the current directory. Flags may appear
before or after a command's positional argument; a surplus argument is a
usage error. `uniac -h` lists commands, and a command's `-h` prints its
usage.

| Invocation | Purpose |
|---|---|
| `uniac init` | Create a starter `uniac.yaml` in the current directory. |
| `uniac plan [--json] [--full] [--dir <path>]` | Validate and preview every deployment in the owning project. |
| `uniac project create <name>` | Create a remote project. |
| `uniac link [-C <path>] [name-or-slug]` | Create or replace the owning project's remote binding. |
| `uniac deploy [--dir <path>]` | Build and deploy every declaration in the owning project. |
| `uniac status [--dir <path>] [service]` | Read a linked project's state, or one named service. |
| `uniac logs <service> [--instance <id>] [-f] [--previous] [--tail <n>] [--since <time>] [--timestamps] [--dir <path>]` | Print what a service's instances write. |
| `uniac exec <service> [--instance <id>] [-i] [--dir <path>] -- <command> [<arg>...]` | Run one command in an instance of a service. |
| `uniac exec -it <service> [--instance <id>] [--dir <path>] -- <command> [<arg>...]` | Run a command in a terminal in an instance of a service. |
| `uniac service delete <name> [--dir <path>] [--silent]` | Delete a service from the linked project. |
| `uniac volume delete <name> [--dir <path>] [--silent]` | Delete a volume and its data from the linked project. |
| `uniac project delete <name> [--silent]` | Delete a remote project and everything in it. |
| `uniac auth <login\|status\|token\|logout>` | Manage [authentication](/cli/authentication). |
| `uniac version` | Print the installed binary's version, commit and build time. |

`--version` and `-v` are aliases for `version`.
[Output](/cli/output) describes result formats, progress and exit codes.

## Local initialization

`init` runs offline and writes a prebuilt-image service definition named
`<name>-definition` and a private deployment declaration `<name>` that
instantiates it; `public_ports` on the declaration adds an endpoint. It prompts
for the service name, previews the file and asks for confirmation;
end-of-input accepts the defaults. The default name comes from
the directory name, with `app` as the fallback. `init` stops when the
directory already has a `uniac.yaml`.

`npm create @uniac@latest` invokes `uniac init` through the `@uniac/create`
package. Initialization is local: it writes `uniac.yaml` and leaves the remote
account unchanged.

## Local project ownership

`plan`, `deploy`, `link`, `status`, `logs` and `exec` resolve the owning
local project from their starting directory. A containing [workspace](/composition/yaml#workspaces-and-packages)
owns its included packages. Without a workspace, the nearest ancestor
`uniac.yaml` owns the standalone project. Above that project, only a
`uniac.yaml` that declares `workspace` can contain it; discovery reads the
others' top-level keys alone. Starting from a member or its subdirectory
selects the same project as starting from the root.

All six commands validate manifest structure and workspace membership.
An unlisted manifest below a workspace and a nested workspace are errors.
`link`, `status`, `logs` and `exec` need only a valid description; deployable workloads,
buildable sources and Docker are requirements of `deploy`.

## Project selection

Deployment addresses an existing
[remote project](/#accounts-projects-and-applications).
`project create <name>` creates one on the authenticated account and prints
its name and assigned slug. It is non-interactive, works from any directory,
and changes only the remote account. The name must match
`^[a-z][a-z0-9-]{0,62}$`. Project creation, deletion and linking use the
platform selected by `UNIAC_PLATFORM_URL`, whose default and credential
selection are described in [Authentication](/cli/authentication).

`link` resolves the local project first. An exact project slug or a uniquely
matching name selects the project directly. Without an argument, `link` opens
the project picker, whatever the number of projects, and several matching
names open it too. The command fails when nothing matches, the account has no
projects, or required input stays unanswered.

Linking writes or replaces `.uniac/deploy.json` at the owning project root:

| Field | Meaning |
|---|---|
| `project_name` | The remote project's account-scoped name, used for platform reads. |
| `project_slug` | The project's assigned identifier. |
| `gateway_url` | The project gateway used for image uploads and deployment requests. |
| `platform_url` | The platform API origin used for credentials and observations. |

All workspace packages share the root's binding; a binding file in a member or
on the path below the root is an error, even when it matches the root binding.
Relinking from any member changes the owner's binding for subsequent
operations. Each operation captures its destination when it starts, so a
concurrent relink applies to later operations. Relinking changes where later
commands deploy; remote services stay where they are.

`deploy`, `status`, `logs`, `exec` and the [service and volume deletes](#deleting-services-volumes-and-projects)
select their destination as follows:

- A nonempty `UNIAC_PROJECT_URL` names a project by its gateway URL or slug,
  in place of the binding, and the platform origin comes from
  `UNIAC_PLATFORM_URL`. The CLI finds that project in the account's project
  listing on that platform and uses its name, slug and gateway; a value that
  names no project on the account fails with `not_linked`.
- Otherwise the binding supplies the project gateway and platform. A
  conflicting explicit `UNIAC_PLATFORM_URL` fails before a network call. A
  binding without `platform_url` uses the selected default platform; one
  without `gateway_url` derives the gateway from its slug.
- Without a binding or override, `deploy` opens the project picker and saves
  the selected binding; `status`, `logs`, `exec` and the service and volume
  deletes report that the project is not linked.

`status` reads the project that the binding or `UNIAC_PROJECT_URL` names.
It reads every service in the project, including services missing
from the local description; whole-project status also reads volumes.

## Planning and deployment

`plan` and `deploy` collect every deployment declaration in the resolved
project's root and included packages, so they always cover the whole project.
Planning requires at least one deployment declaration, and each service comes
from one declaration.

`plan` performs [description validation](/composition/yaml#validation) offline
and needs neither credentials nor Docker. It composes the complete graph and
checks that its build paths exist; image builds and remote checks happen in
`deploy`. `--full` expands the
text preview; `--json` returns the generated description, as specified in
[Output](/cli/output#plan-output).

`deploy` repeats this planning before authentication or remote activity.
Single-service and multi-service projects use the same deployment path.

Deployment additionally requires credentials for the target project's
platform and a reachable local Docker daemon for either `image:` or `build:`.
Before Docker or image work, deployment checks the credential with the
platform. It looks up the project's slug and requires the returned name, slug
and gateway to match the binding, or the project that `UNIAC_PROJECT_URL`
names in the account-level project listing. A saved binding is optional
because deployment can select an existing project interactively.

For [service sources](/resources/service#required-and-optional-configuration), deployment pulls
prebuilt images using local Docker credentials or builds from the current
working tree. Both target `linux/amd64`. The build context's `.dockerignore`
filters its input. Builds run on every deployment and use Docker's layer
cache. The resulting
image is pushed to the project registry and registered with the service
description. Sources remain relative to their defining package. Within one
run, services sharing a source and target platform share image work;
different packages' `build: .` sources remain distinct.

Missing build directories or Dockerfiles fail during local planning.
Dockerfile syntax, missing build stages, failing build commands, image pulls
and daemon availability are checked during image work. Planning checks the
endpoint, environment variable and volume limits that the
[service](/resources/service),
[exposure](/resources/service#networking-and-endpoints) and
[storage](/resources/volume) pages state, and the platform applies those
pages' constraints when the deployment is submitted.

All service images are checked before the first push. Each run submits a new
[deployment version](/resources/service#runtime-and-deployment-versions) of
every declared service, in reference order: a service whose environment
[references](/resources/service#resolution) another declared service is
registered after that service's deployment has settled, so the reference
resolves to the version the same run declared. Services with no reference
between them are registered together before the CLI waits for any of them.
Services that reference each other in a cycle are registered together, and
each resolves the others against the versions serving at that moment.

When registration returns a task ID and the initial task read succeeds, the
CLI polls every two seconds until the task finishes, when the deployment
[succeeds or fails](/resources/service#runtime-and-deployment-versions), or a
five-minute observation deadline passes. Authentication or
access denial fails the command. In other cases, the report shows the accepted
registration without an observed state.

Failure, interruption or the observation deadline stops new local work and
returns partial results: when a deployment does not settle, the services
registered after it are not attempted. Deployments the platform accepted continue, each on its own. An
interrupted or lost registration response leaves acceptance unconfirmed. A
later deploy is a new, independent operation.

After a release attempt, including a partial failure, the CLI writes a local
record of image digests, submission outcomes and receipts under
`~/.uniac/store`; `UNIAC_STORE_DIR` selects another directory.
[Output](/cli/output#partial-observations-and-warnings) describes recording
failures.

## Reading logs

`logs <service>` prints the [logs](/resources/service#logs) of the service's
instances, as the service has them when the command starts. Each line is
prefixed with its instance's short form, which
[Output](/cli/output#log-output) describes with the line format.

| Option | Effect |
|---|---|
| `--instance <id>` | Reads one instance, named by its key or by a start of it that no other instance of the service shares. |
| `-f` | Follows the instances: prints new output as they write it, across restarts, until interrupted. |
| `--previous` | Reads each instance's run before the current one. It cannot be combined with `-f`. |
| `--tail <n>` | Starts each run's output `n` lines before its end, from 0 to 100000. Without it, every kept line is printed. |
| `--since <time>` | Prints only lines received at or after an RFC 3339 time; a time without an offset is UTC. |
| `--timestamps` | Begins each line with the time the platform received it, RFC 3339 in UTC to the second, as [Output](/cli/output#log-output) shows. |

Without `-f`, `logs` prints each instance's current run, or with `--previous`
the run before it, one instance after another in key order, and exits. An
instance without a run prints nothing, and `--previous` on an instance
without a previous run fails that instance's read with `deploy_failed`. With
`-f`, it follows every instance at once and continues into later runs.

The platform ends a followed read after five minutes, and the CLI resumes it
after the last line it received, without missing or repeating a line. It
resumes the same way after a dropped connection. When the credential expires,
the platform ends the read and the CLI's next read fails with `auth`.

When the platform moves a followed instance to another node, the CLI
continues with its runs there; when the instance is removed, its output ends.
While the platform cannot serve an instance's logs, as briefly after a move,
the CLI waits as the platform asks and retries, for up to five minutes of
waiting in a row, and then reports the instance `unreachable`.

Each instance being read holds one open read. An account can hold 10 open
reads and an instance 4; a read beyond either fails with `deploy_failed`,
and its message names the limit it reached.

`logs` selects the project as `status` does and uses its platform's
credentials.

## Running a command

`exec <service> -- <command> [<arg>...]` runs one command in a running
instance of the service, as an [exec](/resources/service#exec), and prints
what the command writes to stdout on stdout and to stderr on stderr, as it
arrives. Everything after `--` is the command's argument list, with no shell
added; `-- sh -c '<script>'` runs a shell the image has. An argument must be
valid UTF-8.

| Option | Effect |
|---|---|
| `--instance <id>` | Runs in one instance, named by its key or by a start of it that no other instance of the service shares. |
| `-i` | Sends the CLI's standard input to the command, read to its end, at most 1 MiB. |
| `-t` | Runs the command in a terminal, as [In a terminal](#in-a-terminal) describes. It requires `-i`; `-it` gives both. |

Without `-t`, the platform stops the command 120 seconds after it starts.

A service with one instance runs the command there. A service with several
needs `--instance`; without it, `exec` runs nothing, and its message lists
the instances by their [short forms](/cli/output#log-output). A service
without instances fails the same way. Each `exec` runs its command once, and
running `exec` again runs the command again.

`exec` exits with the command's exit code. For its own outcomes it uses the
codes `docker exec` uses. A command can exit with the same codes, so each of
these outcomes except an interruption also writes on stderr, as
[Output](/cli/output#exec-output) shows:

| Exit | Condition |
|---|---|
| 125 | The CLI or the platform failed, such as an invalid invocation, a project that is not linked, a missing or rejected credential, a description error, no instance chosen, standard input over 1 MiB, a refused exec, a stream that ended before the command's outcome, a process that could not be started, or an outcome whose exit status the platform did not observe. |
| 126 | The program is not executable. |
| 127 | The program was not found: it is not on the container's `PATH`, its path names no file, or the interpreter its `#!` line names is missing. |
| 130 | The CLI received SIGINT, as from Ctrl-C, or SIGTERM. Either ends the exec, and the platform stops the command's own process. |

An exec is refused when the instance's container is not running, and its
message names the instance's state; when the account holds 4 open execs or
the instance 2, and its message names the limit; and when the platform
cannot run it at the moment. That last refusal can follow a command that
started and was stopped, so run a command that changes data again only once
you know it did not run.

`exec` selects the project as `status` does and uses its platform's
credentials.

### In a terminal

`exec -it <service> -- <command> [<arg>...]` runs the command in a
[terminal](/resources/service#terminal) connected to the CLI's own, such as
`-- sh` for a shell. It requires a terminal on the CLI's standard input, and
the command's arguments together hold at most 512 bytes as UTF-8. The CLI's
terminal is in raw mode once its connection to the platform is open, so
every key reaches the program, Ctrl-C included, and the terminal's size
follows the CLI's window. The terminal ends when the program exits, after 15 minutes
without input, or at 1 hour.

`exec -it` exits with the program's exit code, and otherwise with the codes
above: 125 also covers `-t` without `-i` or without a terminal on standard
input, a command over 512 bytes, a refused terminal, and a connection that
closed before the terminal ended; 130 is SIGINT or SIGTERM sent to the CLI
itself. An end other than the program's own exit writes one line on stderr,
as [Output](/cli/output#exec-output) shows. A terminal is refused as an exec
is, with its own caps of 4 open terminals per account and 2 per instance.

## Deleting services, volumes and projects

`service delete <name>` deletes a service of the linked project, with the
effects in [Dashboard and removal](/resources/service#dashboard-and-removal):
a volume bound to it is unbound and keeps its data.

`volume delete <name>` deletes a volume and its data, with the effects in
[Volume lifecycle](/resources/volume#lifecycle): a volume a service is bound
to is refused. `<name>` is the volume's full name as `status` lists it,
`<service>.<volume>`.

`project delete <name>` deletes a project of the authenticated account, with
the effects in [Project lifetime](/#project-lifetime): its services,
endpoints, and every volume and its data, including unbound volumes. Like
`project create`, it works from any directory.

`service delete` and `volume delete` then poll every two seconds until what
they delete is gone, up to a five-minute deadline, then exit `pending`; the
deletion continues after the deadline or an interruption. A service already
`terminating` or a volume already `deleting` is awaited without the question
below or a new deletion.

`project delete` returns once the platform accepts the deletion. The platform
then removes the project's services, endpoints and volumes, and
`project create` accepts the name again once it has. A repeated
`project delete` finds no project of that name and exits `deploy_failed`. A
directory linked to the deleted project keeps its binding; `deploy`, `status`
and the service and volume deletes there exit `not_linked` until `link`
selects another project.

In a terminal, the three commands show what they delete and ask for its
typed name; any other answer deletes nothing and exits 2. `--silent` skips
the question and changes nothing else. Without a terminal on standard input,
`--silent` is required, and the command exits 2 before any network call.
`service delete` and `volume delete` select the project as `status` does and
use its platform's credentials; `project delete` uses the platform and
credentials of `project create`. [Output](/cli/output#deletion-output)
describes their results.
