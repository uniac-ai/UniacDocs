---
title: "Exit codes"
description: "The typed exit statuses of deploy and status."
---

`uniac deploy` and `uniac status` exit with a status from a closed set, each
paired with an error code. A run that gets as far as reporting also prints
that code — as the `error` row of `status`'s block, and as the annotation on
the root line of `deploy`'s frame (see [Run output](/cli/output#failures)); a
run rejected at argument parsing prints no code at all. Branch on the exit
status; read the code for detail; never match on the message, which is prose
for people.

Within this set **1 is deliberately unassigned**, so a bare `exit 1` from
some future dependency can never be mistaken for a meaning `deploy` or
`status` assigned.

| Exit | `error` code | Meaning | What to do |
|---|---|---|---|
| 0 | — | Success. | Read the state block. |
| 2 | `usage` | Malformed invocation. Nothing was sent anywhere, and nothing reaches stdout: the flag error and the command's usage go to stderr. The code itself is reserved — part of the vocabulary, emitted by nothing. | Fix the arguments. |
| 3 | `auth` | Missing credential — none on disk for the platform the run addresses, none in the environment, or the stored session has expired. A credential the platform *rejects* lands elsewhere; see the disagreements below. | `uniac auth login`, or set `UNIAC_ACCESS_TOKEN`. |
| 4 | `not_linked` | `deploy` reached its **link** phase and the account has no projects, so there is nothing to bind to (nothing was created) — or, from `deploy` and `status` both, the directory's binding and an explicit `UNIAC_PLATFORM_URL` name different platforms, refused before anything goes on the wire. | `uniac project create <name>` for the empty account; unset `UNIAC_PLATFORM_URL` or re-run `uniac link` for the platform disagreement. |
| 5 | `manifest` | `uniac.yaml` is missing from the project directory, or does not describe a valid system. | Add or fix the manifest; `uniac plan` reproduces most of these offline. |
| 6 | `build` | Failed obtaining a container — a pull, a Dockerfile build, or reaching the local Docker daemon. | Read the build board in the frame; check that the daemon is running. |
| 7 | `push` | Failed publishing the image to the project registry. | Retryable. |
| 8 | `deploy_failed` | The platform's deployment task failed. | Terminal unless `retryable` says otherwise — and read the disagreements below. |
| 9 | `unreachable` | The platform did not answer: a transport error, or an edge reporting no origin (502, 503, 504, 521, 522, 523, 530). Nothing was decided either way. | Retry with backoff. |
| 10 | `pending` | Reserved: part of the vocabulary, emitted by nothing. | See the disagreements below. |
| 70 | `internal` | A defect in the CLI — and the code any failure the CLI cannot classify falls back to; read the disagreements below. | Read the message first; report it when the message names nothing you can fix. |

The set is closed and additions are additive — treat any unrecognized code as
`internal` and surface the message rather than guessing.

`deploy` assigns the code by the phase that failed, which decides where a
build problem lands: a service whose `build:` root, context, or `Dockerfile`
is missing exits `5`, because the source is checked while the manifest
resolves and before anything is built — `uniac plan` reproduces that check
offline. `6` is the build itself failing, or no daemon to run it on.

## Where the code and the condition disagree

Four conditions arrive under a code that describes them poorly — one of them
because `pending` is reserved. Read the message before acting on the code:

- `uniac status` in a directory with no link binding, run with a credential,
  exits `70` (`internal`): "project not linked. Run `uniac link` or set
  UNIAC_PROJECT_URL" — not `4`, which needs a binding to disagree with or an
  empty account to stop on. Without a credential the auth check fires first
  and it exits `3` instead; `uniac deploy` never reaches this error, because
  an unlinked directory sends it to the interactive project picker, or to `4`
  when the account is empty. Where the target carries no project name — an
  older binding, or `UNIAC_PROJECT_URL`, which supplies none — `uniac status`
  exits `3` (`auth`): "this directory is not linked to a project. Run
  `uniac link` first".
- Once `deploy` holds a credential, its `link` phase exits `70` (`internal`)
  for every cause but one: a platform it cannot reach, a credential the
  platform rejects, a project picker nobody answered. The code says nothing
  about which one it was — read the `link` child's message. The exception is
  an account with no projects, which exits `4`.
- A deploy still rolling out when the five-minute settle deadline passes exits
  `8` (`deploy_failed`), saying
  `deploy <service>: still <step> after 5m0s — check the dashboard`. The
  rollout continues platform-side, so this `8` is not terminal — the run
  stopped watching, the deployment did not stop. Re-observe with
  `uniac status`.
- `uniac status` exits `8` (`deploy_failed`) when the platform read fails with
  a non-2xx status outside the unreachable set above — a rejected credential
  (401, 403) included. Nothing was deployed, and nothing failed to deploy.

## Other commands

Everything outside `deploy` and `status` is human-oriented and uses plain
statuses: `0` success, `1` error, `2` usage error. That covers `init`,
`plan`, `link`, `project`, and `auth`; `version`, which is always `0`; and a
bare or unknown invocation, which prints the subcommand list to stderr and
exits `2`. `uniac link` on an account with no projects is one of these: it
exits `1`, where the same condition inside `deploy` exits `4`.

An error `uniac plan` raises too — the manifest failing to resolve, or a
`build:` root, context, or `Dockerfile` that does not exist — exits `5` under
`deploy` and `1` under `plan`, with the identical message. Not every `5`
reproduces there; a deployment instantiating more than one service, for one,
passes `plan` and is rejected only by `deploy`. The manifest page lists [what
waits for deploy](/concepts/manifest#what-waits-for-deploy) — the rules `plan`
passes and `deploy` applies.
